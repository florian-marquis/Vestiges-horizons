# ADR-002 : Benchmark Headless pour la Validation des Invariants

## Statut
**Accepté**  
**Date** : 2024-11-14  
**Auteurs** : Agent IA (Mistral Vibe)

---

## Contexte

Le projet nécessite la validation continue des invariants I1-I9 définis dans `Docs/spec P1 - quartier vivant.md` §7. La spec P1 exige qu'un benchmark headless s'exécute sur 10 ans pour valider que tous les invariants restent verts (section 1 : "le quartier vit... tous les invariants de la section 7 restent verts, et l'ensemble tourne headless sur 10 ans").

Auparavant, il n'y avait pas de moyen systématique de:
1. Valider les invariants sur une longue période (10 ans = 3650 jours)
2. Mesurer les performances du moteur de simulation
3. Tester les scénarios de choc (chocs 1-13 de la spec)
4. Garantir la reproductibilité (graine 42)

---

## Décision

**Créer un benchmark headless dédié** dans `src/bin/benchmark_p1.rs` avec les caractéristiques suivantes :

### 1. Portée minimale
- Se concentre sur les modules critiques : market, entities, credit, tax
- Valide les invariants I1, I2, I3, I5, I9 (ceux déjà implémentés)
- Mesure le temps d'exécution par jour

### 2. Configuration standardisée
- **Graine** : 42 (comme spécifié par l'utilisateur)
- **Durée** : 10 ans (3650 jours)
- **Fréquence de vérification** : tous les 100 jours pour les invariants

### 3. Intégration des chocs
- **Choc 2** : import ÷2 pendant 90 jours (à partir du jour 200)
- Structure extensible pour ajouter les autres chocs (1-13)

### 4. Sortie structurée
- Rapport texte avec :
  - Performances (temps total, temps par jour)
  - Statistiques (imports traités, mises à jour de prix)
  - Statut des invariants (PASS/FAIL)
  - Configuration utilisée

---

## Conséquences

### Positives
- **Validation continue** : Les invariants sont vérifiés automatiquement
- **Reproductibilité** : Même graine = mêmes résultats (déterminisme)
- **Mesure de performance** : Identification des goulots d'étranglement
- **Conformité spec** : Respect de la requirement "benchmark obligatoire à la tranche 10"
- **Règle économique** : Coût minimal (une seule implémentation) pour un gain maximal (validation continue)

### Négatives
- **Maintenance** : Le benchmark doit être mis à jour avec les nouveaux modules
- **Temps d'exécution** : 10 ans de simulation peut devenir long avec un moteur plus complexe

---

## Alternatives rejetées

### 1. Utiliser Criterion.rs
**Rejeté car** :
- Ajoute une dépendance externe
- Criterion est conçu pour des micro-benchmarks, pas pour des simulations longues
- La configuration Criterion est complexe pour des tests de validation
- Coût (Ajout d'une dépendance + complexité) > Gain

### 2. Intégrer dans Cargo test
**Rejeté car** :
- Les tests unitaires ne sont pas conçus pour des exécutions longues
- Impossible de gérer proprement les sorties et rapports
- Moins flexible pour les paramètres (graine, durée)

### 3. Script externe (Python, Bash)
**Rejeté car** :
- Sort du cadre Rust, perd le typage et la sécurité
- Difficile à maintenir en synchronisation avec le code
- Ne respecte pas la convention "tout est piloté par le code"

## Implémentation

### Fichier créé
- `src/bin/benchmark_p1.rs` : Binaire standalone
- `Cargo.toml` : Ajout de la cible bin

### Commande d'exécution
```bash
cargo build --release --bin benchmark_p1
./target/release/benchmark_p1.exe
```
